# Moodle JS Actions Collector

Система собирает действия авторизованных пользователей Moodle и показывает их
в таблице и на графике. Moodle работает самостоятельно; наш плагин подключает
браузерный JS-сборщик, который отправляет события в отдельный коллектор
(FastAPI + MongoDB + веб-интерфейс Vue). Общая база данных с Moodle не нужна.

Собираются открытия страниц, клики, прокрутка, видимость вкладки, copy/paste,
факты ввода с клавиатуры, изменения чекбоксов и нативных выпадающих списков.
Сохраняются пользователь, курс, URL, время, User-Agent и метаданные страницы.
HTML-снимки, значения полей, символы клавиатуры и содержимое буфера обмена
текущий сборщик не отправляет.

**Выберите режим:**

- [Локальный стенд](#локальный-стенд) — коллектор и чистый Moodle с демокурсом.
- [Существующий Moodle](#подключение-существующего-moodle) — отдельный коллектор и установка плагина в ваш Moodle.

## Локальный стенд

### 1. Подготовьте окружение

Нужны Docker Engine и Docker Compose **2.20+**. На Windows команды выполняются в WSL. Node.js, PHP и базы на хост
ставить не нужно. Для упаковки отдельного плагина понадобится Python **3.10+**.

Откройте терминал в корне скачанного или склонированного репозитория:

```bash
docker info --format '{{.OSType}}/{{.Architecture}}'
docker compose version
[ -f .env ] || cp .env.example .env
```

Настройки находятся в `.env`. Для первого локального запуска подходят значения
из примера. Если стенд уже работал, сохраните его `.env`: смена
`COMPOSE_PROJECT_NAME` подключит другой набор томов и будет выглядеть как новая
пустая установка. Пароли существующих аккаунтов изменением `.env` не меняются.

### 2. Соберите и запустите

```bash
docker compose pull mongodb mariadb &&
docker compose build --pull=false backend frontend moodle &&
docker compose up -d --no-build --wait --wait-timeout 900
```

Первый запуск устанавливает Moodle **5.0.2**, создает демокурс, пользователей
и включает плагин. Дождитесь завершения команды; установка может занять несколько
минут. Повторная сборка использует Docker cache — это нормально.

**Если сборка зависла на `load metadata` или не скачивается образ:**

Прервите сборку через `Ctrl+C`. При необходимости установите skopeo:

```bash
sudo apt-get update && sudo apt-get install -y skopeo
```

Скачайте проблемный образ вне Docker daemon и импортируйте его. В `image`
укажите образ из строки ошибки; ниже пример для backend:

```bash
image='docker.io/library/python:3.12-slim-bookworm'
image_dir="$(mktemp -d /tmp/collector-image.XXXXXX)" &&
skopeo copy --retry-times 5 \
  "docker://$image" \
  "docker-archive:${image_dir}/image.tar:${image}" &&
docker load --input "$image_dir/image.tar" &&
rm -- "$image_dir/image.tar" &&
rmdir -- "$image_dir"
```

Базовые образы проекта:

| Для чего | Образ |
| --- | --- |
| Backend | `docker.io/library/python:3.12-slim-bookworm` |
| Сборка frontend | `docker.io/library/node:22-bookworm-slim` |
| Веб-сервер frontend | `docker.io/library/nginx:1.28-alpine` |
| Получение исходников Moodle | `docker.io/library/alpine:3.22` |
| Moodle / PHP | `docker.io/library/php:8.3-apache-bookworm` |
| База коллектора | `docker.io/library/mongo:8.0.13` |
| База локального Moodle | `docker.io/library/mariadb:10.11.11` |
| Только E2E-тесты | `mcr.microsoft.com/playwright:v1.63.0-noble` |

После импорта повторите сборку и запуск. Если базы уже скачаны через skopeo,
начните сразу с `docker compose build`, пропустив `docker compose pull`.
`--pull=false` не гарантирует полностью автономную сборку: npm, pip, apt и Git
по-прежнему требуют сеть. Если после импорта снова зависает `load metadata`,
проверьте `docker buildx ls`: отдельный builder может иметь свое хранилище образов.

### 3. Откройте сервисы

| Сервис / роль | Адрес | Логин | Пароль по умолчанию |
| --- | --- | --- | --- |
| Moodle / администратор | http://localhost:18082 | `admin` | `AdminLocal123!` |
| Moodle / студент | http://localhost:18082 | `student` | `StudentLocal123!` |
| Moodle / преподаватель | http://localhost:18082 | `teacher` | `TeacherLocal123!` |
| Интерфейс коллектора | http://localhost:18081 | `collector@example.com` | `CollectorLocal123!` |
| Документация API | http://localhost:18080/docs | — | — |

Пароли берутся из `.env` при создании аккаунтов. Вход в Moodle и вход в коллектор
используют разные учетные записи. Есть также `student2` с паролем студента.

Войдите как `student`, откройте **Collector Demo Course**, почитайте материал,
вставьте текст в задание, переключите вкладку. Затем откройте коллектор, войдите
и нажмите **Обновить**. Должны появиться строки событий с URL этого Moodle.

## Подключение существующего Moodle

Проверена версия **5.0.2**. Плагин требует Moodle **5.0 или новее**; это минимальная
версия установки, а не подтверждение совместимости со всеми будущими версиями.
Для Moodle 4.x этот пакет не подходит. Изменять ядро или тему Moodle не нужно.

### 1. Поднимите только коллектор

Этот пример — отдельная установка на целевом сервере. Она не создает второй
Moodle. Не запускайте ее поверх локального стенда на тех же портах.

```bash
[ -f .env ] || cp .env.example .env
```

Отредактируйте `.env` до первого запуска. Пример адресов — замените своими:

```dotenv
MOODLE_URL=https://moodle.example.org
COLLECTOR_API_URL=https://collector.example.org/api
COLLECTOR_PORT=18081
COLLECTOR_API_PORT=18080
```

| Настройка | Что указать |
| --- | --- |
| `MOODLE_URL` | В этом режиме — origin Moodle для CORS: протокол, домен и порт, если он нестандартный. Без пути и завершающего `/`. Например, для `https://school.example.org/moodle` здесь нужно `https://school.example.org` |
| `COLLECTOR_API_URL` | Публичный адрес API коллектора с `/api`. Он должен открываться из браузера пользователя; его также нужно вручную указать в настройках плагина |
| `COLLECTOR_ADMIN_EMAIL`, `COLLECTOR_ADMIN_PASSWORD` | Учетная запись для входа в интерфейс коллектора; создается при первой инициализации базы |
| `MONGO_ROOT_USER`, `MONGO_ROOT_PASSWORD` | Отдельные учетные данные базы коллектора; не логин Moodle и не пароль интерфейса |
| `COLLECTOR_DB_MAX_SIZE` | Порог хранения данных и индексов базы коллектора. По умолчанию `100GB`; можно указать, например, `500MB`, `10GB` или `100GiB` |

Для новой установки замените пароли из примера. У работающей установки
не меняйте пароли базы только в `.env`: это не меняет учетные записи внутри БД.

```bash
docker compose -f docker-compose.prod.yaml pull mongodb &&
docker compose -f docker-compose.prod.yaml build --pull=false backend frontend &&
docker compose -f docker-compose.prod.yaml up -d --no-build --wait --wait-timeout 900
```

При проблемах скачивания образов используйте блок **skopeo** выше. В этом режиме
не нужны образы локального Moodle, MariaDB и Playwright.

По умолчанию порты доступны только на `127.0.0.1` сервера. Для внешних пользователей
настройте DNS и HTTPS reverse proxy: весь `https://collector.example.org/`,
включая `/api/`, должен идти на `http://127.0.0.1:18081` **на хосте сервера**.
Проверьте, что интерфейс коллектора открывается с компьютера пользователя.
На HTTPS Moodle адрес API также должен быть HTTPS.

Если после запуска меняете origin в `MOODLE_URL`, примените конфигурацию и
обновите адрес backend в nginx:

```bash
docker compose -f docker-compose.prod.yaml up -d --no-build --wait --wait-timeout 900 backend &&
docker compose -f docker-compose.prod.yaml exec -T frontend nginx -s reload
```

### 2. Соберите ZIP плагина

Из корня проекта, на любой машине с Python 3.10+:

```bash
python3 scripts/build-moodle-plugin.py
```

Результат — **`dist/local_actioncollector.zip`**. Скрипт сам добавляет актуальный
`stat_tracker/collector.js`; Docker, npm и доступ к сети для упаковки не нужны.
Тестовая страница `playground.php` в пакет не входит. Созданный ZIP исключен из Git.

### 3. Установите плагин в Moodle

1. Войдите в ваш Moodle под администратором.
2. Откройте **Администрирование → Плагины → Установка плагинов**.
3. Загрузите `dist/local_actioncollector.zip`.
4. Проверьте результат проверки пакета и завершите установку/обновление Moodle.
5. Откройте **Администрирование → Плагины → Локальные плагины → Action collector**.

Прямые страницы относительно адреса вашего Moodle:

- Установка: `/admin/tool/installaddon/index.php`.
- Настройки: `/admin/settings.php?section=local_actioncollector`.

Если установка ZIP запрещена или каталог недоступен для записи, администратор
сервера должен разместить каталог `actioncollector` из архива в
`<каталог кода Moodle>/local/actioncollector`, затем завершить обновление через
**Администрирование → Уведомления**. В Docker файлы должны попасть в постоянный
каталог кода или образ Moodle, чтобы сохраниться при пересоздании контейнера.

### 4. Настройте плагин

| Поле в Moodle | Что сделать |
| --- | --- |
| **Enable collection** | Поставить галочку |
| **Collector API URL** | Вставить адрес API, например `https://collector.example.org/api` |

Нажмите **Сохранить изменения**. В поле API не подходят `localhost` на чужом
компьютере и внутренние Docker-имена вроде `backend:8080`. Этот адрес использует
браузер студента. Плагин действует на весь сайт для вошедших пользователей,
включая преподавателей и администраторов; гостей он не собирает.

### 5. Проверьте сбор

1. Перезагрузите уже открытые вкладки Moodle, войдите обычным пользователем.
2. Откройте курс и задание, нажмите кнопки, прокрутите страницу, введите текст.
3. Откройте интерфейс коллектора, войдите его учетной записью и нажмите **Обновить**.
4. Найдите события по ID пользователя или названию курса и проверьте URL в строках.
5. В окне скачивания выберите **Метаданные страниц в формате json (без HTML)**:
   там должны быть `browser`, `page`, `title`, `window`, без `page_html`.

В консоли браузера на странице Moodle можно проверить `window.actionCollector`:
при успешном запуске `ready` равен `true`, а после доставки `error` равен `null`.

## Тесты, обновление и остановка

E2E выполняются на **локальном демокурсе** и создают события, ответы и попытки:

```bash
bash scripts/test.sh
```

В текущем наборе 18 сценариев. Отчет: `reports/e2e/html/index.html`.
Без повторной сборки тестового образа: `bash scripts/test.sh --no-build`.
Подробнее: [e2e/README.md](e2e/README.md).

Обновление локального стенда после изменения исходников:

```bash
docker compose build --pull=false backend frontend moodle &&
docker compose up -d --no-build --wait --wait-timeout 900 backend frontend &&
docker compose exec -T frontend nginx -s reload &&
docker compose up -d --no-build --wait --wait-timeout 900 moodle
```

Backend обновляется раньше плагина. Во внешнем Moodle заново соберите ZIP,
установите обновление и перезагрузите страницы. Локальный Moodle обновляет плагин
при старте автоматически. Сборка frontend идет из исходников; старый
`client/dist` для этого не нужен.

```bash
bash scripts/start-local.sh  # Запустить уже собранный локальный стенд
bash scripts/stop.sh         # Остановить его, сохранив тома
docker compose ps -a
docker compose logs --tail=100 backend frontend moodle
```

Обновление установки только коллектора:

```bash
docker compose -f docker-compose.prod.yaml build --pull=false backend frontend &&
docker compose -f docker-compose.prod.yaml up -d --no-build --wait --wait-timeout 900 &&
docker compose -f docker-compose.prod.yaml exec -T frontend nginx -s reload
```

Ее остановка: `docker compose -f docker-compose.prod.yaml down`.
Не используйте `down -v` для обычной остановки: флаг `-v` удаляет тома с данными.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| Ошибка CORS | `MOODLE_URL` в конфигурации backend должен совпадать с origin открытого Moodle, без пути и `/` в конце. После изменения примените конфигурацию |
| `window.actionCollector` отсутствует | Вход в Moodle, установка и включение плагина, API URL; затем перезагрузка страницы. При необходимости очистите кэши Moodle |
| Есть `ready: true`, но события не появляются | `error` в объекте сборщика, вкладка Network, доступность API из браузера и **Обновить** в UI |
| HTTP 502 после пересоздания backend | Перезагрузите nginx: `docker compose exec -T frontend nginx -s reload`; в режиме только коллектора добавьте `-f docker-compose.prod.yaml` |
| Не подходит пароль после изменения `.env` | Значение в `.env` не сбрасывает пароль существующего аккаунта |

## Ограничение хранения базы коллектора

В `.env` можно задать:

```dotenv
COLLECTOR_DB_MAX_SIZE=100GB
COLLECTOR_DB_CHECK_INTERVAL_SECONDS=5
```

`GB` и `MB` — десятичные единицы: `100GB` = 100 000 000 000 байт.
Для двоичных единиц используйте `GiB` и `MiB`. Нулевой или некорректный лимит
считается ошибкой конфигурации.

Backend периодически получает MongoDB [`dbStats.totalSize`](https://www.mongodb.com/docs/v8.0/reference/command/dbStats/): выделенное место
под документы **всех коллекций этой базы и их индексы**, включая свободное место
внутри файлов MongoDB. Отдельного запроса проверки на каждое событие нет.
Между измерениями запросы делят общий лимит: учитываются текущие запросы
и запас по размеру тела запроса. Это уменьшает превышение при одновременной отправке.

При исчерпании лимита новые записи событий, метаданных страниц и создание/
изменение пользователей коллектора получают **HTTP 507** с `Retry-After`.
Если проверка объема не удалась или устарела, новые записи получают **HTTP 503**.
Чтение, выгрузки, вход и удаление остаются доступны; существующие данные
автоматически не удаляются. Работа форм Moodle не зависит от результата отправки.

Состояние доступно по `/api/healthcheck/storage`, например:
`http://localhost:18080/api/healthcheck/storage`. Поля `allocated_bytes` и
`estimated_bytes` показывают измеренный размер и оценку с учетом новых запросов;
`accepting_writes` и `reason` — разрешен ли прием. Этот запрос использует кэш
и не запускает дополнительное измерение. Обычный healthcheck `/api/healthcheck/`
продолжает проверять доступность MongoDB и не падает только из-за заполнения лимита.

Это **программный порог приема записей**, а не жесткая квота дискового тома.
Размер может немного превысить порог из-за распределения файлов и параллельных
операций.
Журнал MongoDB, служебные файлы, другие базы, экспорты и Docker-логи в этот размер
не входят. Прямые записи в MongoDB обходят проверку API. лимит между измерениями
общий для одного процесса backend; для нескольких процессов/реплик превышение
может быть больше. Текущая конфигурация запускает один процесс.

## Текущие ограничения

Сборщик 1.1.1 работает с ограничениями на каждое открытие страницы:

| Ограничение | Значение |
| --- | --- |
| Очередь, включая отправляемую пачку | До 500 событий и 256 КиБ сериализованных событий |
| Одна пачка | До 20 событий и 48 КиБ полного JSON-запроса |
| Обычная отправка | Не чаще одного запроса в секунду на вкладку |
| После ошибки | Паузы 2, 4, 8, 16, до 30 секунд, с небольшим случайным разбросом |

При переполнении отбрасываются старые ожидающие события. Отправляемая пачка
сохраняется до результата запроса; слишком большое отдельное событие отбрасывается.
На уходе со страницы разрешена одна попытка вне обычного интервала, но без обхода
паузы после ошибки. Запросы коллектора не ожидаются при сохранении ответов Moodle.
Скрипт загружается с `async` и не задерживает `DOMContentLoaded` своим скачиванием.

В консоли `window.actionCollector` показывает `queued`, `queuedBytes`, `sent`,
`dropped`, `retryAt`, `error`. `queuedBytes` — размер сериализованных событий,
не полный размер объектов в RAM. `dropped` считает явное отбрасывание по лимитам,
сбрасывается при переходе на новую страницу и пока не сохраняется на сервере.
Он не измеряет неизвестные потери при закрытии вкладки или потере ответа API.

Очередь находится только в памяти вкладки: при сбое и закрытии возможны потери,
при повторной отправке — дубли. Если регистрация страницы трижды не удалась,
сборщик на этой странице не запускается до перезагрузки. Гарантии «потеряется
не больше 1–2 событий» нет. Автоудаления по сроку нет; события клавиатуры
увеличивают объем данных. URL передается целиком; ФИО и email также сохраняются.
Для разных Moodle используйте отдельные экземпляры коллектора со своими базами:
отдельного `site_id` нет.

Старые HTML-поля в MongoDB автоматически не удаляются; API их не выгружает,
но `mongo_export.sh` читает базу напрямую и может включить исторический HTML.
Выгрузки больших наборов пока загружают данные в RAM и используют общие файлы.

Авторизация и права на стороне API пока не реализованы; пароли пользователей
коллектора хранятся открытым текстом. Вход в UI сам по себе не закрывает API.
